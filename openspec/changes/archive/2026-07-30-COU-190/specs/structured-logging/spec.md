# Structured Logging System Specification

## Purpose

This specification defines the structured logging system for the backend-nosql-standard-project. It unifies Fastify Pino and NestJS ConsoleLogger into a single `nestjs-pino` instance with automatic correlation ID propagation from Fastify `req.id` to all application logs. The system provides structured JSON logging in production with pretty-printed output in development, and supports log suppression in test environments.

## Requirements

### Requirement: Unified Logging Module Configuration

The system MUST use `nestjs-pino`'s `LoggerModule.forRoot()` to configure a single Pino instance shared between Fastify HTTP logger and NestJS application logger.

The `AppModule` SHALL import and configure `LoggerModule.forRoot()` with environment-driven settings:
- Production: `pinoHttp.level` set to environment variable `LOG_LEVEL` (default: 'info')
- Test: `pinoHttp.level = 'silent'` when `NODE_ENV='test'`
- Development: Enable `pino-pretty` transport for readable console output

#### Scenario: LoggerModule Configuration

- GIVEN `AppModule` imports
- WHEN `LoggerModule.forRoot()` is configured with proper environment settings
- THEN Fastify and NestJS log to the same Pino instance
- AND production logs use structured JSON output
- AND development logs use pretty-printed output for readability
- AND test environment produces no log output

### Requirement: Correlation ID Propagation

The system MUST automatically propagate Fastify `req.id` (hyperid UUID from `genReqId`) into all Pino log entries for trace correlation.

The correlation ID SHALL be:
- Generated by `genReqId` middleware (existing)
- Available as `req.id` on Fastify request object
- Propagated by `nestjs-pino` to all `PinoLogger` injections
- Included as `traceId` or `req.id` field in all structured log entries

#### Scenario: Correlation ID in HTTP Logs

- GIVEN an incoming HTTP request
- WHEN `genReqId` middleware processes the request
- THEN `req.id` is set to a unique UUID
- AND Fastify HTTP logs include `req.id` field

#### Scenario: Correlation ID in Application Logs

- GIVEN a service or filter requiring trace correlation
- WHEN code logs via `@InjectPinoLogger()`
- THEN the log entry contains the same `req.id` as the originating HTTP request
- AND development logs show correlation between HTTP and application events

### Requirement: PinoLogger Dependency Injection

The system MUST replace all `CustomLogger` usages with `@InjectPinoLogger()` from `nestjs-pino`.

All classes SHALL use `PinoLogger`:
- `AllExceptionsFilter`: Inject `PinoLogger` instead of `new Logger()`
- `EntityRepository`: Replace `CustomLogger` with `PinoLogger`
- `EncodeService`: Remove dead logger property
- `MicroserviceFactory`: Replace `CustomLogger` with `PinoLogger`

#### Scenario: AllExceptionsFilter PinoLogger Injection

- GIVEN a NestJS application with global exception handling
- WHEN `AllExceptionsFilter` is instantiated
- THEN it injects `PinoLogger` for structured error logging
- AND logs include correlation ID in error responses

#### Scenario: EntityRepository PinoLogger Usage

- GIVEN `EntityRepository` requires logging for seed operations
- WHEN services call logging methods
- THEN logs use injected `PinoLogger` with structured format
- AND seed errors include correlation context

### Requirement: Test Environment Log Suppression

The system MUST suppress Pino log output when running in test environment.

When `NODE_ENV='test'`, the configuration SHALL set:
- `pinoHttp.level = 'silent'` in `LoggerModule.forRoot()`
- All Pino log levels set to 'silent'
- No log output to stdout/stderr during test execution
- Test logs written to files or captured for assertions when needed

#### Scenario: Test Environment Log Silence

- GIVEN `NODE_ENV='test'` environment variable
- WHEN application starts with `LoggerModule.forRoot()`
- THEN `pinoHttp.level` is set to 'silent'
- AND no Pino logs appear in test output

#### Scenario: Development Environment Pretty Printing

- GIVEN `NODE_ENV='development'` environment variable
- WHEN application starts with `LoggerModule.forRoot()`
- THEN `pino-pretty` transport is enabled
- AND console output is human-readable (colored, formatted)

### Requirement: Log Output Format

The system MUST provide structured JSON logging in production and pretty-printed logging in development.

Production output SHALL be:
- JSON format with fields: timestamp, level, message, req.id/traceId, context, etc.
- Level-based filtering (debug, info, warn, error)
- Sanitized/redacted fields via Pino configuration
- Consistent across all logging sources

Development output SHALL be:
- Human-readable console output with colors
- Timestamp and level indicators
- Pretty-printed JSON for easier reading

#### Scenario: Production JSON Log Format

- GIVEN production environment setup
- WHEN application logs an error event
- THEN log output is valid JSON with structured fields
- AND includes all relevant metadata (traceId, context, error details)

#### Scenario: Development Pretty Print Format

- GIVEN development environment
- WHEN application logs an info event
- THEN console shows colored, formatted log output
- AND JSON is pretty-printed for readability

### Requirement: Fastify Logger Configuration Delegation

The system MUST delegate Fastify adapter logging configuration to `LoggerModule.forRoot()`.

The `main.ts` configuration SHALL:
- Remove direct `logger: { ... }` config from Fastify adapter
- Delegate to `LoggerModule.forRoot()` configuration
- Preserve existing redaction, timestamp, and level settings in Pino configuration

#### Scenario: Fastify Logger Migration

- GIVEN `main.ts` has Fastify logger config
- WHEN `nestjs-pino` integration is enabled
- THEN Fastify adapter logger is removed from `main.ts`
- AND all logging configured through `LoggerModule.forRoot()`
- AND redaction, sanitization, timestamp behavior preserved

## Non-requirements

The following are OUT OF SCOPE for this change:

- OpenTelemetry / distributed tracing integration
- Log aggregation (ELK, Loki, Datadog)
- Custom log levels beyond Pino defaults
- File transport / log rotation
- Log shipping or external log analysis tools
- Advanced async log forwarding
- Structured log analysis or visualization tools
- Log-based monitoring dashboards

## Affected Domains

This specification affects the following domains:

1. **structured-logging**: New logging system with Pino integration
2. **error-handling**: Modified to use PinoLogger for structured error logging
3. **common-errors**: Enhanced with correlation ID propagation

## Compliance with OpenSpec Standards

This spec follows OpenSpec conventions:
- Uses Given/When/Then format for scenarios
- RFC 2119 keywords (MUST, SHALL, SHOULD, MAY)
- At least one happy path and one edge case scenario per requirement
- Testable scenarios that can be automated
- No implementation details included (only WHAT, not HOW)
